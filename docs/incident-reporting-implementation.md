# Incident reporting workflow / ঘটনা প্রতিবেদন কর্মপ্রবাহ

## English

The authenticated `/incidents` route provides private organization-scoped intake and response. An active organization member may submit a report with title, description, category, initial severity, occurrence/detection times, affected system, impact summary and evidence notes. New reports begin in `submitted`.

Reports are readable by their submitter and the organization owner, admin or lead reviewer. Other organization members cannot read a report merely because they share the organization. Owners/admins/lead reviewers can change severity and status, assign an active organization member, and record containment, investigation/root cause, response, remediation and closure rationale. Closure or dismissal requires a rationale. The workflow states are `submitted`, `triage`, `investigating`, `response`, `monitoring`, `closed` and `dismissed`. Every create, status/management update, comment, evidence note, file upload and signed download-link issuance adds a timestamped audit event. Signed URLs and raw storage keys are not written to those events.

Incident reporters and authorized managers may attach one file at a time, up to 10 MiB each. Accepted types are PDF, JPEG, PNG, GIF, WebP, plain text, DOC/DOCX and XLS/XLSX. The server validates the declared MIME type, encoded payload, size and file signature. SVG and other unlisted formats are rejected. Uploads are rate-limited, rejected for closed/dismissed incidents, and written to project object storage under random organization/incident-scoped keys. The additive `incident_evidence` metadata table stores uploader, display filename, MIME type, byte count, storage key and timestamp. Application responses do not return storage keys or unsigned storage-path URLs.

Evidence metadata is listed only after the same report visibility check used for incident details. A temporary signed download URL is issued only after checking current reporter/manager access and confirming the evidence belongs to the incident and organization. Each link issuance is recorded in the incident timeline without the URL. This audits link issuance, not whether a recipient fetched the object; actual fetch auditing requires storage-provider access logs. The uploaded file itself is not malware-scanned; do not upload credentials, secrets, or unnecessary personal data. If the object upload succeeds but the subsequent metadata transaction fails, an unreferenced object can remain because this project does not currently expose an object-delete helper.

This tool is an internal reporting aid, not a regulator notification channel, legal advice or certification. Additive migration `drizzle/0009_incident_evidence.sql` creates the evidence metadata table and indexes; `drizzle/0010_incident_evidence_audit.sql` adds the `evidence_link_issued` event value. Both were generated and consistency-checked but not applied. Do not apply them outside the approved staging migration process (`pnpm db:migrate`) after confirming the target and backup/rollback plan. Authenticated multi-tenant upload/download tests, real storage integration, URL-expiry checks and body-parser verification remain staging work; no live/shared database was changed while preparing this source update.

## বাংলা

প্রমাণীকরণ-সুরক্ষিত `/incidents` route-এ প্রতিষ্ঠানের অভ্যন্তরীণ ঘটনা প্রতিবেদন ও প্রতিক্রিয়া পরিচালনা করা যায়। সক্রিয় প্রতিষ্ঠানের সদস্য শিরোনাম, বিবরণ, ধরন, প্রাথমিক তীব্রতা, ঘটনার/শনাক্তের সময়, প্রভাবিত সিস্টেম, প্রভাবের সারাংশ এবং প্রমাণের নোটসহ প্রতিবেদন দিতে পারেন। নতুন প্রতিবেদন `submitted` অবস্থায় শুরু হয়।

প্রতিবেদনটি প্রতিবেদক এবং প্রতিষ্ঠানের owner, admin বা lead reviewer দেখতে পারেন। শুধু একই প্রতিষ্ঠানের সদস্য হওয়ার কারণে অন্য সদস্য প্রতিবেদন দেখতে পারেন না। Owner/admin/lead reviewer তীব্রতা ও অবস্থা পরিবর্তন, সক্রিয় সদস্যকে তদন্তের দায়িত্ব, ক্ষতি-নিয়ন্ত্রণ, তদন্ত/মূল কারণ, প্রতিক্রিয়া, প্রতিকার এবং বন্ধের কারণ নথিভুক্ত করতে পারেন। বন্ধ বা খারিজ করতে কারণ দিতে হয়। ধাপগুলো হলো `submitted`, `triage`, `investigating`, `response`, `monitoring`, `closed` এবং `dismissed`। প্রতিবেদন তৈরি, ব্যবস্থাপনার পরিবর্তন, মন্তব্য, প্রমাণের নোট, ফাইল আপলোড এবং signed download-link issuance timestamp-সহ audit timeline-এ যোগ হয়। Signed URL বা raw storage key audit event-এ রাখা হয় না।

প্রতিবেদক ও অনুমোদিত ব্যবস্থাপক একবারে একটি করে সর্বোচ্চ ১০ MiB ফাইল যুক্ত করতে পারেন। PDF, JPEG, PNG, GIF, WebP, plain text, DOC/DOCX এবং XLS/XLSX গ্রহণ করা হয়। সার্ভার MIME type, encoded payload, file size এবং signature যাচাই করে; SVG বা তালিকার বাইরের ধরন বাতিল হয়। Upload rate-limit করা, বন্ধ/খারিজ প্রতিবেদনে নতুন ফাইল যোগ করা নিষিদ্ধ, এবং ফাইল random organization/incident-scoped key-তে project object storage-এ রাখা হয়। Additive `incident_evidence` টেবিলে uploader, প্রদর্শিত filename, MIME type, byte count, storage key ও সময় থাকে। Application response-এ storage key বা unsigned storage-path URL দেওয়া হয় না।

প্রমাণের তালিকা দেখাতে incident detail-এর একই access check প্রয়োগ হয়। Temporary signed download URL দেওয়ার আগে reporter/manager access এবং file-টি ওই incident ও organization-এর কি না যাচাই করা হয়। প্রতিটি link issuance URL ছাড়া audit timeline-এ লেখা হয়। এটি link তৈরি হওয়া নথিভুক্ত করে, recipient সত্যিই object download করেছে কি না তা নয়; প্রকৃত fetch audit করতে storage provider-এর access log দরকার। File malware scan করা হয় না—পাসওয়ার্ড, গোপন তথ্য বা অপ্রয়োজনীয় ব্যক্তিগত তথ্য আপলোড করবেন না। Storage upload সফল হলেও পরবর্তী metadata transaction ব্যর্থ হলে orphan object থেকে যেতে পারে, কারণ এই project-এ object-delete helper নেই।

এটি প্রতিষ্ঠানের অভ্যন্তরীণ প্রতিবেদন সহায়তা; নিয়ন্ত্রক সংস্থায় আনুষ্ঠানিক নোটিশ, আইনি পরামর্শ বা সার্টিফিকেশন নয়। Additive migration `drizzle/0009_incident_evidence.sql` evidence metadata table ও index তৈরি করে; `drizzle/0010_incident_evidence_audit.sql` `evidence_link_issued` event value যোগ করে। দুটিই generate ও consistency-check হয়েছে, কিন্তু apply করা হয়নি। target database এবং backup/rollback পরিকল্পনা নিশ্চিত করে অনুমোদিত staging প্রক্রিয়ায় (`pnpm db:migrate`) চালাতে হবে। Authenticated multi-tenant upload/download পরীক্ষা, real storage integration, URL expiry check এবং request body-parser verification staging-এ বাকি; এই source পরিবর্তনের সময় live/shared database পরিবর্তন করা হয়নি।
